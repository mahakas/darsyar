# راهنمای کامل راه‌اندازی درسیار در ویندوز — مخصوص مبتدی‌ها

**نسخهٔ این راهنما:** 2026-11-12  
**مخزن:** https://github.com/mahakas/darsyar  
**وضعیت محصول:** در حال توسعه؛ این راهنما محیط توسعهٔ محلی را راه‌اندازی می‌کند و به معنی آماده‌بودن محصول برای استفادهٔ عمومی یا Production نیست.

این راهنما برای کسی نوشته شده که تجربهٔ برنامه‌نویسی یا Docker ندارد. مراحل را به‌ترتیب انجام بده و تا وقتی مرحله‌ای درست نشده، سراغ مرحلهٔ بعد نرو.

---

## ۱. اول بدان قرار است چه چیزی نصب شود

درسیار از چند سرویس جدا تشکیل شده است:

| بخش | وظیفهٔ ساده |
|---|---|
| Frontend | صفحه‌ای که در مرورگر می‌بینی |
| API | مغز اصلی برنامه و ارتباط بین بخش‌ها |
| PostgreSQL + pgvector | نگهداری کاربران، گفتگوها، داده‌ها و بردارهای جست‌وجو |
| Redis | صف و داده‌های موقت و محدودسازی درخواست‌ها |
| Worker | اجرای کارهای پس‌زمینه |
| Inference | سرویس embedding و reranking برای جست‌وجوی هوشمند |
| Migrate | اجرای یک‌بارهٔ تغییرات ساختار پایگاه داده |

این سرویس‌ها با Docker Compose اجرا می‌شوند. لازم نیست PostgreSQL یا Redis را جداگانه روی ویندوز نصب کنی.

**نکتهٔ مهم دربارهٔ هوش مصنوعی:** بالا آمدن وب‌سایت به‌تنهایی به معنی آماده‌بودن چت هوشمند نیست. برای کارکرد چت به تنظیمات یک ارائه‌دهندهٔ مدل زبانی (LLM) نیاز است. برای آماده‌شدن سرویس Inference نیز یا باید API سازگار برای embedding معرفی شود یا مدل‌های محلی بارگذاری شوند.

## ۲. پیش‌نیازهای کامپیوتر

نسخه‌های مورد استفادهٔ مخزن در زمان تهیهٔ راهنما:

- Windows 10 یا Windows 11 نسخهٔ ۶۴ بیتی.
- Git.
- Docker Desktop با پشتیبانی WSL 2 و Docker Compose v2.
- توزیع Ubuntu روی WSL 2 (مسیر پیشنهادی برای ویندوز).
- Python 3.13 برای اجرای ابزارهای Python خارج از Docker.
- uv برای مدیریت محیط و وابستگی‌های Python.
- Node.js نسخهٔ 24 و npm برای ابزارهای Frontend.

نسخه‌های دقیق و وضعیت فعلی را همیشه در `docs/TECH_STACK.md` و `docs/DEVELOPMENT_SETUP.md` ببین.

### منابع سخت‌افزاری

در یک بررسی محلی ثبت‌شده در مخزن، دستگاهی با حدود ۸ گیگابایت RAM هنگام بارگذاری مدل‌های محلی inference با کمبود حافظه مواجه شد. بنابراین:

- اگر RAM دستگاهت محدود است، از حالت remote برای embedding/reranking و یک API سرویس‌دهندهٔ مدل استفاده کن.
- حالت مدل محلی می‌تواند دانلود بزرگ مدل و مصرف RAM/CPU زیادی داشته باشد.
- مقدار RAM و فضای دیسک موردنیاز به مدل، تنظیمات و محیط اجرا وابسته است؛ مخزن حداقل سخت‌افزاری قطعی و تضمین‌شده‌ای برای همهٔ دستگاه‌ها اعلام نکرده است.

## ۳. نصب ابزارها در ویندوز

### ۳.۱. نصب Git

1. از وب‌سایت رسمی Git for Windows نصب‌کننده را دریافت کن: https://git-scm.com/download/win
2. مراحل نصب را با گزینه‌های پیش‌فرض ادامه بده.
3. از منوی Start برنامهٔ **Git Bash** را باز کن.
4. این دستور را اجرا کن:

```bash
git --version
```

باید شمارهٔ نسخه نمایش داده شود.

### ۳.۲. نصب WSL 2 و Ubuntu

1. منوی Start را باز کن و **PowerShell** را با گزینهٔ **Run as administrator** اجرا کن.
2. این دستور را وارد کن:

```powershell
wsl --install -d Ubuntu
```

3. اگر ویندوز درخواست راه‌اندازی مجدد کرد، Restart کن.
4. پس از نصب، Ubuntu را از منوی Start باز کن.
5. برای Ubuntu یک نام کاربری و رمز عبور بساز. هنگام تایپ رمز، نمایش داده نمی‌شود؛ این رفتار طبیعی است.
6. در Ubuntu این دستور را اجرا کن:

```bash
sudo apt update
sudo apt install -y git make curl ca-certificates
```

برای بررسی WSL از PowerShell استفاده کن:

```powershell
wsl --status
wsl --list --verbose
```

Ubuntu باید در حالت Version 2 باشد. اگر نسخهٔ ۱ نشان داده شد:

```powershell
wsl --set-version Ubuntu 2
```

### ۳.۳. نصب Docker Desktop

1. از صفحهٔ رسمی Docker Desktop برای Windows نصب‌کننده را دریافت کن: https://www.docker.com/products/docker-desktop/
2. هنگام نصب، گزینهٔ استفاده از WSL 2 را فعال نگه دار.
3. Docker Desktop را اجرا کن.
4. در Settings بخش **Resources → WSL Integration**، اتصال توزیع Ubuntu را فعال کن.
5. مطمئن شو Docker Desktop باز است و وضعیت Engine روی Running قرار دارد.

در ترمینال Ubuntu اجرا کن:

```bash
docker --version
docker compose version
docker run --rm hello-world
```

اگر دستور آخر پیام موفقیت نشان داد، Docker آماده است.

### ۳.۴. نصب Python 3.13 و uv

Python 3.13 را از منبع رسمی نصب کن: https://www.python.org/downloads/

در ترمینال مناسب، نسخه را بررسی کن:

```bash
python --version
```

باید Python 3.13.x باشد. سپس uv را طبق دستور رسمی نصب کن: https://docs.astral.sh/uv/getting-started/installation/

در Ubuntu معمولاً می‌توانی دستور نصب رسمی Linux را از همان صفحه اجرا کنی. سپس ترمینال را ببند و دوباره باز کن و اجرا کن:

```bash
uv --version
```

### ۳.۵. نصب Node.js 24

Node.js نسخهٔ 24 را از منبع رسمی دریافت و نصب کن: https://nodejs.org/

در ترمینال اجرا کن:

```bash
node --version
npm --version
```

نسخهٔ Node باید 24.x باشد.

**پیشنهاد:** پروژه را در فایل‌سیستم Ubuntu نگه دار، نه در مسیر `/mnt/c`؛ این کار معمولاً از کندی و مشکلات سازگاری ابزارها جلوگیری می‌کند.


برای اطمینان از قرارگرفتن در پوشهٔ درست:

```bash
pwd

```

شاخهٔ پیش‌فرض مخزن `main` است.

برای بازکردن پروژه در VS Code، در صورت نصب افزونهٔ WSL و فرمان `code`:

```bash

```

در VS Code باید پایین پنجره اتصال به WSL را ببینی.

فایل `.env.example` فقط الگو است و نباید همان‌طور برای اجرای واقعی استفاده شود.

در ریشهٔ پروژه:

```bash
cp .env.example .env
```

سپس فایل را با ویرایشگر باز کن:

```bash
code .env
```

یا:

```bash
nano .env
```

### ۵.۱. تولید سه رمز تصادفی مستقل

این سه مقدار باید از هم متفاوت باشند:

- `APP_SECRET_KEY`
- `OTP_PEPPER`
- `POSTGRES_PASSWORD`

در Ubuntu این دستور را سه بار اجرا کن تا سه رشتهٔ hex مستقل تولید شود:

```bash
openssl rand -hex 32
```

هر خروجی را در جای درست فایل `.env` قرار بده. خروجی‌ها را برای کسی ارسال نکن و در Git ثبت نکن.

### ۵.۲. هماهنگ کردن رمز PostgreSQL

در `.env` مقدار `POSTGRES_PASSWORD` را با رمز تصادفی سوم جایگزین کن.

همان رمز باید در هر دو URL زیر نیز جایگزین بخش رمز شود:

```dotenv
DATABASE_URL=postgresql+asyncpg://darsyar:رمز-تو@localhost:5432/darsyar
TEST_DATABASE_URL=postgresql+asyncpg://darsyar:رمز-تو@localhost:5432/darsyar_test
```

چون خروجی `openssl rand -hex 32` فقط شامل حروف و عددهای hex است، برای قرار دادن در URL دردسر کاراکترهای ویژه را نخواهی داشت.

**هر سه مقدار باید دقیقاً هماهنگ باشند.** اگر رمز PostgreSQL را تغییر دادی ولی URLها را تغییر ندادی، اتصال تست‌ها به دیتابیس برقرار نمی‌شود.

### ۵.۳. پیکربندی ارائه‌دهندهٔ embedding — مرحلهٔ ضروری

در فایل نمونه، مقادیر زیر به صورت remote انتخاب شده‌اند اما آدرس و کلید آن‌ها خالی است:

```dotenv
EMBEDDING_BACKEND=remote
EMBEDDING_REMOTE_BASE_URL=
EMBEDDING_REMOTE_API_KEY=
EMBEDDING_REMOTE_MODEL=
```

سرویس Inference برای Ready شدن به هر سه مقدار نیاز دارد. تا وقتی آن‌ها را از ارائه‌دهندهٔ سرویس embedding دریافت نکرده‌ای و وارد نکرده‌ای، سرویس Inference سالم نمی‌شود و API نیز به دلیل وابستگی Compose ممکن است بالا نیاید.

- `EMBEDDING_REMOTE_BASE_URL`: آدرس پایهٔ API سازگار با قرارداد embedding این پروژه.
- `EMBEDDING_REMOTE_API_KEY`: کلید محرمانهٔ همان سرویس.
- `EMBEDDING_REMOTE_MODEL`: نام دقیق مدل embedding که ارائه‌دهنده اعلام کرده است.

کد فعلی درخواست را به مسیر `/embeddings` در آدرس پایه می‌فرستد و ابعاد خروجی باید با `EMBEDDING_DIM=1024` سازگار باشد. آدرس، مدل و ابعاد را از مستندات رسمی ارائه‌دهنده بگیر؛ حدس نزن.

اگر ارائه‌دهندهٔ rerank هم در اختیار داری، این مقادیر را نیز تنظیم کن:

```dotenv
RERANK_BACKEND=remote
RERANK_REMOTE_BASE_URL=
RERANK_REMOTE_API_KEY=
RERANK_REMOTE_MODEL=
```

قرارداد rerank فعلی مسیر `/rerank` را انتظار دارد. سرویس باید پاسخ سازگار با قرارداد کد پروژه برگرداند. صرفاً داشتن API embedding به معنی پیکربندی rerank نیست.

**راه جایگزین:** اگر می‌خواهی مدل‌ها داخل کامپیوتر خودت اجرا شوند، باید backend محلی را آگاهانه انتخاب کنی و منابع سخت‌افزاری و دانلود مدل‌ها را در نظر بگیری. `EMBEDDING_BACKEND=service` باعث بارگذاری BGE-M3 و BGE-Reranker-v2-M3 در سرویس Inference می‌شود. این حالت برای رایانهٔ کم‌حافظه توصیه نمی‌شود و در سابقهٔ تست محلی مخزن، دستگاه ۸ گیگابایتی با OOM مواجه شده است. این گزینه را بدون آگاهی از مصرف منابع انتخاب نکن.

### ۵.۴. پیکربندی مدل زبانی برای چت

برای دریافت پاسخ از مدل زبانی، مقادیر زیر نیز باید با اطلاعات ارائه‌دهندهٔ خودت تکمیل شوند:

```dotenv
LLM_PROVIDER=nvidia
LLM_BASE_URL=
LLM_API_KEY=
LLM_MODEL=
```

مقدار `LLM_PROVIDER` باید با provider پشتیبانی‌شده در کد و تنظیمات سرویس تو هماهنگ باشد. این پروژه در خط پایهٔ فعلی providerهای `nvidia` و `openai` را تعریف می‌کند.

تا قبل از واردکردن کلید، URL و نام مدل معتبر، ممکن است صفحهٔ وب باز شود ولی درخواست چت موفق نشود. هیچ کلید API واقعی را در GitHub یا در پیام عمومی قرار نده.

### ۵.۵. پیامک و پرداخت

برای ارسال OTP واقعی از طریق Kavenegar به `KAVENEGAR_API_KEY` و `KAVENEGAR_OTP_TEMPLATE` معتبر نیاز است. تا وقتی این اطلاعات فراهم نشده، ارسال پیامک واقعی را تست‌شده فرض نکن.

پرداخت در فایل نمونه روی حالت sandbox قرار دارد. از اطلاعات پرداخت واقعی یا حساب واقعی در تست محلی استفاده نکن.

### ۵.۶. محافظت از فایل `.env`

- فایل `.env` را commit یا push نکن.
- آن را در تصویر یا فایل ZIP عمومی قرار نده.
- اگر کلیدی اشتباهاً منتشر شد، آن را فوراً در سرویس‌دهنده باطل و جایگزین کن.
- مقادیر `CHANGE_ME` نمونه‌اند و اعتبارنامهٔ واقعی نیستند.
- در این راهنما هیچ رمز یا کلید واقعی درج نشده است.

## ۶. پیش از اجرای Docker، تنظیمات را بررسی کن

در ریشهٔ پروژه اجرا کن:

```bash
docker compose config --quiet
```

اگر خطایی دربارهٔ متغیرهای خالی، رمز یا YAML دیدی، آن را برطرف کن. اجرای این دستور صرفاً صحت ترکیب تنظیمات Compose را بررسی می‌کند و به معنی سالم‌بودن API، مدل یا پایگاه داده نیست.

همچنین بررسی کن این سه مقدار خالی نباشند:

- `EMBEDDING_REMOTE_BASE_URL`
- `EMBEDDING_REMOTE_API_KEY`
- `EMBEDDING_REMOTE_MODEL`

مگر اینکه عمداً حالت local/service را برگزیده باشی.

## ۷. اجرای برنامه

پیش از ادامه، مطمئن شو Docker Desktop باز است و اتصال آن به Ubuntu برقرار است.

از ریشهٔ پروژه اجرا کن:

```bash
make up
```

این دستور سرویس‌ها را build و در پس‌زمینه اجرا می‌کند. ساخت نخستین تصویرها ممکن است حجم زیادی داده دریافت کند؛ به‌خصوص تصویر Inference که وابستگی‌های ML را نصب می‌کند.

بعد وضعیت سرویس‌ها را بررسی کن:

```bash
make ps
make health
```

`make health` فقط وقتی موفق است که سرویس‌های مورد انتظار در وضعیت مناسب باشند؛ سرویس یک‌بارهٔ migration باید با exit code صفر خاتمه یافته باشد و سرویس‌های دائمی باید healthy باشند.

### آدرس‌های محلی

| بخش | آدرس |
|---|---|
| وب‌سایت | http://127.0.0.1:5173 |
| API | http://127.0.0.1:8000 |
| سلامت API | http://127.0.0.1:8000/health |
| آمادگی API | http://127.0.0.1:8000/ready |
| مستندات API در محیط توسعه | http://127.0.0.1:8000/docs |

اگر صفحهٔ وب باز نشد، ابتدا `make ps` و سپس `make logs` را بررسی کن.

## ۸. فرمان‌های روزمره

تمام فرمان‌های زیر را از پوشهٔ اصلی `darsyar` اجرا کن:

| فرمان | کاربرد |
|---|---|
| `make help` | نمایش فرمان‌های موجود |
| `make ps` | نمایش وضعیت کانتینرها |
| `make health` | کنترل سلامت سرویس‌ها |
| `make logs` | نمایش زندهٔ گزارش سرویس‌ها |
| `make up` | ساخت و اجرای سرویس‌ها |
| `make down` | متوقف کردن سرویس‌ها بدون حذف داده‌های volume |
| `make restart` | راه‌اندازی مجدد سرویس‌ها |
| `make migrate` | اجرای migration پایگاه داده |
| `make test` | اجرای تست‌های backend؛ بخشی از تست‌های وابسته به DB ممکن است در این حالت skip شوند |
| `make test-db` | اجرای تست‌های backend با PostgreSQL واقعی Docker |
| `make lint` | اجرای lint بخش backend و frontend |
| `make typecheck` | بررسی نوع‌های backend و frontend |
| `make coverage` | اجرای تست همراه گزارش پوشش هدف‌گذاری‌شده |
| `make smoke` | اجرای smoke test تعریف‌شده در پروژه |

اگر کد را تغییر دادی و لازم است تصویرها دوباره ساخته شوند:

```bash
docker compose up --build -d
```

## ۹. اجرای تست‌ها

ابتدا سرویس‌ها باید اجرا باشند و PostgreSQL و Redis سالم باشند. سپس:

```bash
make lint
make typecheck
make test
make test-db
```

- `make test` بیشتر تست‌های مستقل را اجرا می‌کند؛ بعضی آزمون‌های یکپارچه به دیتابیس واقعی نیاز دارند.
- `make test-db` از فایل `.env` مقدار `TEST_DATABASE_URL` را می‌خواند، دیتابیس تست را آماده می‌کند، migration را اجرا می‌کند و pytest را با PostgreSQL واقعی اجرا می‌کند.
- SQLite جایگزین معتبر تست‌های پایگاه دادهٔ این پروژه نیست.
- تست‌های محیطی مانند sandbox/cgroup یا مدل‌های واقعی ممکن است در CI عمومی به‌دلیل نبود محیط یا منابع لازم skip شوند. تعداد skip را با PASS اشتباه نگیر.

## ۱۰. مشاهدهٔ خطاها و عیب‌یابی اولیه

اگر برنامه بالا نیامد، این سه فرمان را اجرا کن:

```bash
make ps
make health
make logs
```

برای بررسی یک سرویس خاص، مثلاً inference:

```bash
docker compose logs --tail=200 inference
```

برای مشاهدهٔ API:

```bash
docker compose logs --tail=200 api
```

### خطاهای متداول

**الف) Docker daemon در دسترس نیست**

Docker Desktop را باز کن، صبر کن Engine در وضعیت Running قرار بگیرد و دوباره `docker compose ps` را اجرا کن.

**ب) پیام مربوط به POSTGRES_PASSWORD**

فایل `.env` را بررسی کن. مقدار `POSTGRES_PASSWORD` باید خالی نباشد و URLهای دیتابیس هم باید همان رمز را داشته باشند.

**ج) سرویس inference روی unhealthy می‌ماند**

اگر backend از نوع remote است، هر سه مقدار URL، API key و model embedding را بررسی کن. در حالت remote خالی‌بودن هر کدام مانع Ready شدن inference است. اگر مدل محلی انتخاب شده، گزارش دانلود مدل، حافظه و خطای OOM را بررسی کن.

**د) API به inference وابسته است و بالا نمی‌آید**

در Compose، API به healthy بودن inference وابسته است. اول خطای inference را رفع کن؛ Restart پیاپی API بدون رفع علت کمکی نمی‌کند.

**هـ) healthcheck وضعیت سالم نشان نمی‌دهد**

`make ps` و log همان سرویس را بررسی کن. سرویس migration یک‌بار اجرا می‌شود و باید با کد صفر خارج شود؛ انتظار running دائمی از آن درست نیست.

**و) صفحهٔ وب باز می‌شود ولی چت جواب نمی‌دهد**

تنظیمات `LLM_BASE_URL`، `LLM_API_KEY` و `LLM_MODEL`، دسترسی شبکه و سهمیهٔ ارائه‌دهنده را بررسی کن. تنظیمات embedding/rerank نیز برای قابلیت‌های بازیابی لازم‌اند.

**ز) تست دیتابیس متصل نمی‌شود**

روشن‌بودن سرویس postgres، مقدار `TEST_DATABASE_URL`، رمز، نام کاربر و پورت 5432 را بررسی کن. مطمئن شو رمز URL با `POSTGRES_PASSWORD` یکی است.

**ح) پورت 5173، 8000، 5432 یا 6379 اشغال است**

برنامه‌ای که از آن پورت استفاده می‌کند را شناسایی و متوقف کن یا تغییر پورت را با بررسی هم‌زمان Compose، URLها و مستندات انجام بده. تغییر تصادفی یک پورت در یک فایل کافی نیست.

## ۱۱. توقف و نگهداری داده‌ها

برای متوقف‌کردن سرویس‌ها:

```bash
make down
```

این دستور کانتینرها را متوقف می‌کند اما volumeهای پایگاه داده را حذف نمی‌کند.

**هشدار بسیار مهم:** این دستور را بدون فهم پیامد آن اجرا نکن:

```bash
docker compose down -v
```

گزینهٔ `-v` volumeها را حذف می‌کند و ممکن است داده‌های محلی PostgreSQL و Redis را برای همیشه از بین ببرد.

فایل‌های کتاب واقعی، اطلاعات کاربران و secrets را داخل Git قرار نده. قبل از هر عملیات پاک‌سازی یا تغییر ساختار، از داده‌های مهم نسخهٔ پشتیبان بگیر.

## ۱۲. چه چیزهایی در این نسخه هنوز آماده نیست؟

راه‌اندازی موفق محیط توسعه به معنی تکمیل همهٔ فازها نیست. بر اساس وضعیت مستند مخزن در تاریخ این راهنما:

- فازهای ۰ تا ۳ تکمیل شده‌اند.
- فاز ۴ هنوز برای ingestion واقعی کتاب‌ها gated است؛ مسیر عملیاتی کامل دریافت و پردازش PDF پذیرفته نشده است.
- فاز ۵ هنوز به دیتاست طلایی حداقل ۱۵۰ پرسشی، evidence snapshot و اتصال کامل evidence به پاسخ چت نیاز دارد.
- فاز ۶ هنوز به نمایش امن منبع/استناد، Markdown امن، دسترس‌پذیری و پذیرش کامل رابط نیاز دارد.
- فاز ۷ فقط زیرساخت محدود مجوز مدیر و audit را دارد؛ پنل مدیریت، routeهای مدیریتی و acting session کامل نشده‌اند.
- فاز ۸ طبق تصمیم پروژه خارج از MVP و به تعویق افتاده است.
- فاز ۹ هنوز به TLS واقعی، backup/restore، آزمون بار، triage امنیت زنجیرهٔ تأمین، مجوزهای حقوقی و تأیید Production نیاز دارد.

**کتاب‌های آزمایشی را پردازش نکن.** مرجع مجوز 13529 در اسناد پروژه ثبت شده، اما شواهد مستند و دامنهٔ مجوز عملیات هنوز مستقلاً تأیید نشده‌اند. وضعیت فعلی کتاب‌ها `needs_review` است. تا وقتی Gateهای مربوطه رسماً بسته نشده‌اند، دانلود، استخراج، OCR، رندر، embedding یا index کردن PDF واقعی مجاز فرض نمی‌شود.

هیچ مسیر عملیاتی ingestion یا پنل ادمین را صرفاً به خاطر وجود فایل یا مستندات، آماده و فعال فرض نکن.
