# ADR-044: ترکیب Redis (سرور/کلاینت/صف) — تصمیم تأییدشدهٔ مالک

- **وضعیت:** accepted (تصمیم مالک، 2026-10-27)
- **تاریخ:** 2026-10-27 (بازبینی بستن فاز صفر)
- **هم‌راستا با:** R-034، R-035، R-188، R-028؛ سطر «Redis server» در `docs/TECH_STACK.md` را به‌روزرسانی می‌کند (طبق ترتیب قدرت مراجع R-001).

## زمینه

پروژهٔ شروع `redis>=6.0.0,<7.0.0` را پین کرده بود؛ هنگام تولید lockfile واقعی (`uv lock`)، حل‌کننده ناسازگاری واقعی کشف کرد: `arq` (الزام R-188) در آخرین نسخهٔ خود (0.28.0) به `redis[hiredis]>=4.2.0,<6` نیاز دارد، بنابراین `redis>=6` با `arq` قابل حل نیست. بررسی ماتریس رسمی `redis-py` نشان داد کلاینت 5.x فقط تا Redis 7.4 را پشتیبانی می‌کند، در حالی که `redis:8-alpine` سرور 8.10.3 بالا می‌آورد.

## تصمیم تأییدشدهٔ مالک (گزینهٔ ۲ در بازبینی پیشین)

- **نسخهٔ هدف Redis Server: `7.4.12`** — دقیقاً `redis:7.4.12-bookworm`.
- کلاینت `redis-py 5.3.1` و `arq 0.28.0` بدون تغییر می‌مانند (هر دو در رنج پشتیبانی متقابل با سرور 7.4.12 قرار دارند).
- digest تولید `redis:7.4.12-bookworm`: `sha256:bd28fff4b665fdf1b73e8b5b73ec05d2f858f4fa3c8ea0d7c9bc09f7f6bf7039` (برای پین production).
- هیچ نسخهٔ دیگری (PostgreSQL 18، Python 3.13، Node 24، React 19، Vite 8) به‌خاطر این تصمیم تغییر نمی‌کند.

## چرایی انتخاب

- `redis-py 5.x` فقط تا Redis 7.4 را به‌صورت رسمی پشتیبانی می‌کند؛ 7.4.12 بالاترین پچ پایدار این شاخه است.
- `arq 0.28.0` با `redis<6` کار می‌کند و در برابر Redis 7.4 در محدودهٔ تحت‌آزمون آن قرار دارد.
- تغییر سرور روی پچ/minor (نه major برخلاف گزینهٔ «8.x») نیازمند ADR بود و هیچ وابستگی دیگری را نمی‌شکند.

## گزینه‌های ردشده

| گزینه | چرا رد شد |
|---|---|
| حفظ سرور 8.10.3 با کلاینت 5.3.1 | جفت خارج از پشتیبانی رسمی redis-py؛ ریسک رفتاری/امنیتی ناشناخته |
| سرور 8.x + کلاینت 6.x + انتظار برای arq | در حال حاضر با arq قابل حل نیست (قید `redis<6`) |
| کلاینت دوگانه (6 در API، 5 در worker) | پیچیدگی و دو سطح نگهداری؛ مشکل arq باقی می‌ماند |
| فورک/پچ محلی arq | انحراف از upstream و هزینهٔ نگهداری بلندمدت |
| صبر برای upstream arq بدون تغییر | وابستگی به زمان‌بندی شخص ثالث؛ تصمیم رسمی مالک خواستار حل امروز بود |

## پیامدها

- `docker-compose.yml` و `REDIS_IMAGE_TAG` به `redis:7.4.12-bookworm` تغییر کرد (tag دقیق، هرگز `latest`).
- در مهاجرت از سرور 8.10 به 7.4، فایل‌های AOF/RDB placeholder (خالی) ساخت Redis 8 (RDB format 15) توسط Redis 7.4 قابل خواندن نبود؛ پیش از شروع، از volume نسخهٔ پشتیبان گرفته شد و فقط همان placeholderهای خالی پاک شد؛ volume حذف نشد و `docker compose down -v` اجرا نشد؛ هیچ دادهٔ واقعی از دست نرفت.
- وقتی `arq` از `redis>=6` پشتیبانی کند، ارتقا به کلاینت 6+ و در صورت تمایل مالک بازگشت به سرور 8.x با ADR جدید و تست کامل انجام می‌شود (R-035).
- Redis همچنان هرگز منبع حقیقت مالی نیست (R-028/R-124).
