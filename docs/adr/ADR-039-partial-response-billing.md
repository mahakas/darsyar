# ADR-039: پاسخ ناقص و کردیت — تأییدشده (سیاست داخلی زمان اجرا)

- **وضعیت:** accepted (تصمیم مالک — 2026-10-29؛ ثبت OQ-008)
- **هم‌راستا با:** R-132، R-133، R-134، R-145

## زمینه

provider ممکن است پیش از نخستین توکن یا میان استریم شکست بخورد. سیاست داخلی «جبران کردیت هوش مصنوعی» برای زمان اجرا تأیید می‌شود؛ این سند سند حقوقی/تجاری مشتری نیست.

## تصمیم تأییدشده — سیاست داخلی runtime کردیت

1. **آستانهٔ MVP:** `MIN_BILLABLE_TOKENS = 1` — مقدار پیکربندی، نه ثابت hard-coded سرویس.
2. مبنای تصمیم: **توکن‌های محتوای دستیار مشاهده‌شده محلی** (بدون خروجی خالی/فقط-فضای‌خالی)؛ استفاد provider جایگزین خروجی تولیدشده نیست.
3. پاسخ موفق غیرخالی → settle؛ بدهی یک‌کردیت حفظ می‌شود.
4. پیش از رسیدن به آستانه → release رزرو + معکوس‌سازی بدهی با refund.
5. لغو کاربر یا قطع اتصال **پس از** رسیدن به آستانه → settle + حفظ بدهی.
6. timeout/5xx/شکست استریم provider یا خطای داخلی سرور **پس از** آستانه → ثبت نتیجهٔ جزئی settle + **refund جبران** طبق R-133.
7. نبود usage از provider، قاعدهٔ یک‌کردیت را تغییر نمی‌دهد؛ usage provider جدا ذخیره می‌شود؛ برآوردهای محلی با پرچم `estimated` مشخص می‌شوند و به‌عنوان مقدار واقعی ارائه نمی‌شوند.
8. retry پس از نتیجهٔ commit‌شده → بدون تکرار رویداد ledger/usage.
9. پیش از شروع استریم، شکست می‌تواند با وضعیت خطای HTTP برگردد؛ پس از ارسال هدرها، نتیجه با رویداد پایانی مناسب استریم بیان می‌شود و به HTTP 500/499 تغییر نمی‌کند.

## ماتریس تصمیم (خلاصه)

| حالت | پیش از آستانه | پس از آستانه |
|---|---|---|
| بق موفق غیرخالی | — | settle؛ حفظ بدهی |
| لغو کاربر/قطع کلاینت | release + refund | settle؛ حفظ بدهی |
| شکست provider/سرور | release + refund (R-134) | settle + refund جبران (R-133) |
| خروجی خالی/whitespace | release + refund | — (آستانه صعود نمی‌کند) |

تفکیک کلیدی: **لغو/قطع از سمت کاربر/کلاینت** در برابر **شکست از سمت provider/سرور** — فقط مورد دوم پس از آستانه refund جبران می‌گیرد.

## مرز با سیاست بازپرداخت مشتری (R-145)

- این ADR فقط «جبران کردیت داخلی هوش مصنوعی» را برای پیاده‌سازی runtime تأیید می‌کند.
- شرایط مشتری‌محور (بازپرداخت پرداخت‌ها، کردیت استفاده‌نشده، لغو، زمان‌بندی پاسخ، اختلافات) همچنان در `docs/REFUND_POLICY.md` تأیید**نشده** می‌مانند و **گیت انتشار** تولید هستند.

## پیامدها و انتظار تست

- تست‌های مرز `MIN_BILLABLE_TOKENS` (۰/۱/۲)؛ ماتریس حالات با provider mock؛ قطع استریم؛ خطای میانی؛ فlag estimated؛ retry بدون تکرار؛ رویداد پایانی استریم پس از ارسال هدر.
- فایل‌های متأثر: quota service، streaming API، usage_events، refund internal service، تست‌های چت.
